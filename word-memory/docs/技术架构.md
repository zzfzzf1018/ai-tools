# 技术架构

本文说明项目的分层、数据流、渲染策略与构建管线，供二次开发参考。

---

## 1. 设计原则

| 原则 | 具体做法 |
| --- | --- |
| **运行时零依赖** | 不用 React/Vue，不引入运行时库。单文件版约 678 KB；EXE 内置的 HTTP 服务也只用 Node 内置模块 |
| **逻辑与视图分离** | `src/core` 不引用任何 DOM API，可在 Node 中直接 import 测试 |
| **单一数据源** | 会话状态在 `store` 中，视图是状态的纯函数映射；账户 / 词库关系在 `workspace` 中 |
| **一份模板，三个产物** | `src/index.html` 通过三个占位符注入外链或内联资源；EXE 复用 Web 产物 |
| **存储后端可替换** | 前端只依赖同步 KV 接口，浏览器与本地文件两种实现共用一套业务逻辑 |
| **数据可复现** | 词库管道不含时间戳等易变字段，同样输入必得同样输出 |

## 3. 数据流

```
                  ┌──────────────┐
                  │ words.json   │
                  └──────┬───────┘
                         │ createWordbook()
                         ▼
┌────────────┐    ┌──────────────┐    ┌──────────────┐
│  KV / 文件  │◄──►│    store     │◄──►│   session    │
└────────────┘    └──────┬───────┘    └──────┬───────┘
                         │                   │
      workspace ─────────┤（提供当前账户×词库的键与词库内容）
                         ▼                   ▼
                  ┌──────────────────────────────┐
                  │        buildCtx()            │
                  │  聚合：overview + settings    │
                  │   + workspaceInfo + session   │
                  └──────────────┬───────────────┘
                                 ▼
                  ┌──────────────────────────────┐
                  │   VIEWS[state.view](ctx)     │
                  │   → HTML 字符串 → innerHTML  │
                  └──────────────┬───────────────┘
                                 ▼
                  ┌──────────────────────────────┐
                  │  事件委托 → actions → 改状态  │
                  └──────────────────────────────┘
```

一次点击的完整链路（以「评分」为例）：

1. 按钮带 `data-action="grade" data-grade="2"`
2. 根节点上的委托监听器匹配到 `[data-action]`
3. 调用 `actions.grade(el)` → `submitGrade(2)`
4. `session.submit(2)` → `store.recordReview()` → `srs.review()` 算出新状态
5. `store.bumpDaily()` 累加当日统计
6. `loadCard()` 为下一张卡生成题目
7. `render()` 重新渲染整个视图

## 4. 状态管理

应用状态集中在 `createApp()` 闭包内的 `state` 对象：

```js
state = {
  view: 'today',          // 当前视图
  session: null,          // 学习会话对象（含队列）
  question: null,         // 当前题目
  phase: 'quiz',          // 'quiz' | 'reveal'
  picked: '',             // 用户作答
  feedback: null,         // 'correct' | 'wrong'
  browse: { query, filter, level, page, pageSize },
}
```

持久状态（跨会话）在 `store` 中，两者职责清晰：

- `state` 是**会话级**的，刷新即丢（除了 view 通过 URL hash 保留）
- `workspace` 是**工作区级**的（账户表、词库表、激活关系），写入 KV
- `store` 是**持久化**的，按当前 (账户, 词库) 写入 KV；切换工作区时会重建实例

## 5. 渲染策略

### 5.1 全量重渲染 + 焦点恢复

每次状态变化都重新生成整个视图的 HTML 并赋给 `innerHTML`。

优点是简单、不会有「局部更新漏掉某处」的 bug；代价是丢失 DOM 状态（焦点、光标位置、滚动位置）。

补偿措施：

```js
const scroll = mainEl.scrollTop;
const activeId = document.activeElement?.id;
const selection = document.activeElement?.selectionStart;

viewRoot.innerHTML = VIEWS[state.view](ctx);

mainEl.scrollTop = scroll;
if (activeId) {
  const el = document.getElementById(activeId);
  el.focus();
  el.setSelectionRange(selection, selection);
}
```

这样在搜索框里连续打字时，每次输入触发重渲染后光标仍然在原位。

### 5.2 事件委托

只在 `root` 上绑定一次 `click` 监听，通过 `event.target.closest('[data-action]')` 找到触发元素：

```js
delegate(root, 'click', '[data-action]', (event, el) => {
  actions[el.dataset.action]?.(el);
});
```

这样重渲染不会丢事件，也不需要每次渲染后重新绑定。

### 5.3 局部更新的例外

两处例外，因为它们不需要重建 DOM：

- `[data-setting]` 输入框：只更新 store，不重渲染（避免打断输入）
- `#spell-input`：只同步 `state.picked`，不重渲染

多页列表（词库 8000 词）用分页而非虚拟滚动：每页 50 行，渲染成本约 3–5 ms，滚动体验完全可接受，代码量却少了一个数量级。

## 6. 存储层

### 6.1 两层存储：KV 与 adapter

v2 把「数据存在哪」与「学习状态怎么组织」拆开：

```
createBrowserKV() / createHttpKV()        ← 后端：快照 + 异步落盘
        │  get / set / remove / keys / flush（同步读、异步写）
        ▼
createKVAdapter(kv)                       ← 适配成 store 需要的 adapter
        ▼
createStore({ adapter, key, settingsKey })
```

| 适配器 | 用途 |
| --- | --- |
| `createKVAdapter(kv)` | v2 默认，背后是 IndexedDB / localStorage / HTTP 文件服务 |
| `createLocalAdapter(localStorage)` | v1 兼容路径（未传 workspace 时） |
| `createMemoryAdapter()` | Node 测试、隐私模式降级 |

浏览器后端选择顺序：`IndexedDB → localStorage → 内存`。启动时把全部 KV 一次性读入内存快照，之后所有读写都是同步的，只有落盘是异步串行队列——这样 `store` 与 UI 完全不需要改成 async。

`createStore` 新增可选 `settingsKey`：传入时，学习记录与账户设置写到两个不同的键，切换词库不会重置偏好；不传时保持 v1 的单键行为，旧的 15 个存储测试因此无需修改。

降级到内存后界面仍可正常使用，只是明确提示「无法自动保存进度，请导出备份」。

### 6.2 自动保存

写入不是每次操作都落盘，而是标记 dirty 后用 400 ms 防抖合并：

```
操作 → markDirty() → 重置定时器
                     ↓ 400ms 无操作
                   save()
```

另外在 `visibilitychange → hidden`、`beforeunload`、`pagehide`、切换账户/词库、导出全量备份时强制 `flushAll()`（先 `store.flush()`，再 `kv.flush()` 等待异步写入完成），避免切走页面丢数据。

### 6.3 只存变化

默认状态（`s=0, star=0, seen=0, lapse=0`）不写入存储。首次打开应用时 `words` 是空对象，占用几乎为 0。只有在用户真正开始学习后才逐条增加。

8000 词全部学完时约占用 700–900 KB。v2 默认使用 IndexedDB（配额通常为磁盘空间的百分比），因此可以同时存放多个自定义词库与多个账户的进度，不再受 localStorage 5 MB 限制；每个 (账户, 词库) 组合各自一份记录，互不叠加。

## 7. 构建管线

```
src/main.js ──esbuild(bundle,minify,iife)──► dist/web/assets/app.js
src/styles/main.css ──esbuild(minify)─────► dist/web/assets/app.css
src/index.html ──替换占位符───────────────► dist/web/index.html
data/words.json ─────────────────────────► dist/web/data/words.json
                        │
                        └──内联──► dist/word-memory.html（单文件）
```

### EXE 便携版管线（v2.1 · Electron）

```
dist/web/**  ──collectAssets()──► 虚拟模块 virtual:assets（JS 常量）
desktop/electron/main.mjs + server.mjs + env.mjs
        │
        ├──esbuild(bundle, cjs, platform=node, external:electron)──► dist/electron-app/main.cjs
        ├──makeIcon(256)──► dist/electron-app/icon.ico
        └──package.json（写明 electron 版本）
                │
                ▼
electron-builder --win portable ──► dist/electron-out/WordMemory.exe
                │
                └──copy──► dist/WordMemory.exe + dist/exe-info.json
```

关键点：

- 静态资源（含 8000 词 JSON）在构建时变成 JS 字符串常量，运行时不读磁盘上的 `dist/`
- 主进程保持 CJS（electron 作为 external 由运行时提供），无顶层 `await`，用 `main().catch()` 启动
- `electron-builder.yml` 指定 `electronDist: node_modules/electron/dist`，避免打包时重复下载二进制；`ELECTRON_OVERRIDE_DIST_PATH` 同理
- portable 启动器会设置 `PORTABLE_EXECUTABLE_DIR`，主进程用它定位数据目录；`process.execPath` 此时指向自解压的临时目录，**不能**用来推数据位置
- `scripts/build-exe.mjs --bundle-only` 只跑 esbuild，供 Linux CI 快速校验主进程，不产出 EXE
- v2.0 的 Node SEA 管线保留在 `scripts/build-sea.mjs`，产物 `dist/sea/WordMemory.exe`，作为无 Electron 依赖时的备用方案

### CI 中的 EXE 构建

```
tag word-memory-v* ──┬─► build(ubuntu)      测试 → HTML → 发布说明
                     ├─► build-exe(windows) npm ci → build:exe → verify:exe → 上传 EXE
                     ├─► release(ubuntu)    HTML + EXE + exe-info.json → GitHub Release
                     └─► pages(ubuntu)      部署 Web 版
```

Linux 任务设 `ELECTRON_SKIP_BINARY_DOWNLOAD=1`，Windows 任务缓存 `%LOCALAPPDATA%\electron\Cache` 与 `electron-builder\Cache`。
EXE 构建失败时 `release` 仍会发布 HTML（带 warning），避免阻塞常规版本。

模板中的三个占位符：

| 占位符 | Web 版替换为 | 单文件版替换为 |
| --- | --- | --- |
| `<!--APP_CSS-->` | `<link rel="stylesheet" href="assets/app.css">` | `<style>…</style>` |
| `<!--APP_DATA-->` | 空 | `<script>window.__WORD_DATA__=…</script>` |
| `<!--APP_JS-->` | `<script src="assets/app.js"></script>` | `<script>…</script>` |

### 踩过的坑：`String.replace` 的 `$` 语义

最初写成：

```js
template.replace('<!--APP_JS-->', `<script>${js}</script>`)
```

结果单文件版一打开就报 `Unexpected token '<'`。

原因：压缩后的 JS 里含有 `$&`（esbuild 把变量名压成了 `$`，出现了 `$&K(...)` 这样的代码）。而 `String.prototype.replace` 的**替换字符串**里，`$&` 表示「匹配到的子串」，于是 `<!--APP_JS-->` 被原样插回了脚本中间。

修复：所有替换改用函数形式，返回值不再被解析为替换模式。

```js
template.replace('<!--APP_JS-->', () => `<script>${js}</script>`)
```

`scripts/verify.mjs` 里的「单文件版可独立启动」用例，就是用 jsdom 真实执行产物来防这类问题的回归。

### 内联安全处理

```js
function safeInline(text) {
  return text.replace(/<\/script/gi, '<\\/script').replace(/<\/style/gi, '<\\/style');
}
```

防止字符串里意外出现的 `</script>` 提前闭合标签。

## 8. 三版本一致性

三个版本跑的是**同一份 JS、同一份 CSS、同一份数据**，差别只在资源加载方式与存储后端：

| 版本 | 词库来源 | 存储后端 |
| --- | --- | --- |
| Web 版 | `fetch('data/words.json')` | IndexedDB（降级 localStorage / 内存） |
| 单文件 HTML 版 | `window.__WORD_DATA__` | 同上 |
| EXE 便携版 | 内置服务提供的 `data/words.json` | HTTP KV → EXE 同目录文件 |

- 便携版通过 `window.__WM_PORTABLE__` 标记识别，由 `createHttpKV()` 接管 KV
- 其余业务逻辑、视图、算法三者完全一致

`src/main.js` 里的分支：

```js
async function loadPayload() {
  if (window.__WORD_DATA__) return window.__WORD_DATA__;
  const res = await fetch(new URL('data/words.json', document.baseURI));
  return res.json();
}
```

这意味着任何功能改动只需验证一次逻辑，不会出现「网页版能用、单文件版不行」的分裂。

### 为什么单文件版必须用普通 `<script>`

`file://` 协议下浏览器的模块加载受 CORS 限制，`<script type="module">` 会被拒绝执行。所以 esbuild 输出格式选择 **IIFE** 而非 ESM，单文件版直接内联为普通脚本即可。

## 9. 性能

| 场景 | 耗时 | 说明 |
| --- | --- | --- |
| 词库加载与索引 | ~30 ms | 8000 条转小写 + 分频段桶 |
| 首屏渲染 | ~15 ms | 今日页 |
| 词库列表渲染 | ~5 ms | 每页 50 行 |
| 全库搜索 | ~2 ms | 8000 条线性扫描 |
| 队列构建 | ~4 ms | 遍历 8000 条 + 排序 |
| 统计计算 | ~3 ms | 遍历一次聚合 |

这些都是毫秒级，所以没有做缓存、虚拟列表等优化——保持代码可读性更重要。

唯一需要留意的是 `getState()` 返回副本（浅拷贝 11 个字段），在 8000 次循环里会产生 8000 个小对象。实测影响在 2 ms 以内，可接受。

## 11. v2：工作区切换与便携服务

### 11.1 为什么 store 要能「重建」

切换账户 / 词库时，词库内容和学习记录同时改变。做法是让 `createApp` 内的 `wordbook` 与 `store` 变成 `let`，由 `bindWorkspace()` 重新实例化：

```js
function bindWorkspace() {
  const accountId = workspace.activeAccountId();
  const bookId = workspace.activeBookId(accountId);
  wordbook = createWordbook(workspace.bookPayload(bookId) || workspace.builtinPayload);
  store = createStore({
    adapter: createKVAdapter(workspace.kv),
    key: workspace.progressKey(accountId, bookId),
    settingsKey: workspace.settingsKey(accountId),
  });
  loadResult = store.load();
}
```

`buildCtx()` 每次渲染都取当前的 `store` / `wordbook`，因此所有视图无需感知切换。切换动作的顺序是：

```
flushAll() → workspace.setActiveAccount / setActiveBook
          → 清空会话与筛选状态 → bindWorkspace() → render()
```

因为 KV 是同步内存快照，切换不需要 await；落盘由后台队列保证顺序。

### 11.2 便携版服务

`desktop/server.mjs` 是一个不依赖任何 npm 包的 `node:http` 服务：

| 接口 | 作用 |
| --- | --- |
| `GET /`、`/assets/*`、`/data/words.json` | 内嵌静态资源；首页注入一次性令牌 |
| `GET /api/snapshot` | 返回全部 KV（读取 `kv/*.json`） |
| `POST /api/kv` | `{key, value}`，`value: null` 表示删除；临时文件 + rename 原子写 |
| `POST /api/ping` | 心跳（SEA 备用版用于空闲退出；Electron 版保留接口但由窗口生命周期管理） |
| `POST /api/shutdown` | 关闭服务并触发退出回调 |

所有 `/api/*` 校验 `x-wm-token`，所有请求校验 `Host`；服务只 bind `127.0.0.1`，端口由 OS 随机分配。前端每次 `store.flush()` 经 `createKVAdapter → kv.set → fetch('/api/kv')` 落到文件，所以关页前必须 `flushAll()` 并等待 `kv.flush()`。

### 11.4 Electron 主进程生命周期

```
app.whenReady()
   └─ resolveDataDir(WM_DATA_DIR → PORTABLE_EXECUTABLE_DIR → exe 目录 → home)
        └─ createPortableServer(...).listen(0)
             ├─ 写 runtime.json / wordmemory.log
             ├─ WM_HEADLESS=1 → 不建窗口，服务保持进程存活（CI / 冒烟测试）
             └─ 正常模式 → buildMenu() → createWindow(url)
                              ├─ ready-to-show → show()
                              ├─ close → 保存 window-state.json
                              └─ closed → window-all-closed → app.quit()
app.before-quit → service.close() + 删除 runtime.json
```

几个刻意的设计：

- **不把数据访问改成 IPC**：保留 HTTP + 文件 KV，让三端共用同一份代码路径与已验证的安全模型；Electron 只负责窗口与生命周期。
- **单实例锁**：`app.requestSingleInstanceLock()` 防止两个进程写同一数据目录；已有实例被再次启动时把窗口前置。
- **headless 模式**：GUI 程序 stdout 不可靠，端口通过 `runtime.json` 传递；同时禁用 GPU/沙箱以便在 CI 的无桌面会话中启动。
- **`ELECTRON_RUN_AS_NODE` 防御**：从 Electron 宿主派生的终端常带此变量，会让 `require('electron')` 只返回路径字符串；主进程显式检测并报错，测试脚本启动前清除该变量。
- **外链处理**：`will-navigate` 与 `setWindowOpenHandler` 把非本机地址的跳转交给系统浏览器，避免应用内打开任意网页。
