# 测试与发布

本文说明测试体系、产物校验、CI 工作流与发布流程。

---

## 1. 测试分层

```
┌─────────────────────────────────────────────┐
│  真实浏览器  e2e.mjs / e2e-exe.mjs           │  Chrome 跑完整用户路径
├─────────────────────────────────────────────┤
│  EXE 冒烟    verify-exe.mjs                  │  真实启动 EXE + HTTP 校验
├─────────────────────────────────────────────┤
│  产物校验    verify.mjs                      │  jsdom 真实加载单文件版
├─────────────────────────────────────────────┤
│  界面集成    ui.test.js / ui-workspace.test.js│  jsdom + 真实事件
├─────────────────────────────────────────────┤
│  数据校验    data.test.js / bookparse.test.js │  词库完整性与导入解析
├─────────────────────────────────────────────┤
│  单元测试    kv / workspace / portable /     │  纯函数，无 DOM
│              srs / store / scheduler /       │
│              quiz / stats / session          │
└─────────────────────────────────────────────┘
```

运行：

```bash
npm test              # 单元 + 集成 + 数据（141 个用例）
npm run verify        # 以上全部 + 构建 + 产物校验
npm run build:exe     # 构建 Web 产物 + Electron 版 dist/WordMemory.exe
npm run build:sea     # 备用：Node SEA 版 dist/sea/WordMemory.exe
npm run verify:exe    # EXE 冒烟（13 项，需先 build:exe；CI 会跑）
npm run test:e2e      # Web 版真实浏览器端到端（需先 build）
npm run test:e2e:exe  # EXE 版真实浏览器端到端（需先 build:exe）
node scripts/build-exe.mjs --bundle-only  # 只校验主进程可打包（Linux CI）
```

### 2.15 `scripts/e2e.mjs` — Web 版浏览器端到端（18 项）

用 playwright-core 驱动系统 Chrome/Edge，在真实浏览器中走一遍完整用户路径：

学 8 张卡 → 等待落盘 → 刷新验证持久化 → 标记掌握 → 标记重点 → 搜索 → 修改设置 → 导出备份 → 清空进度 → 导入恢复 → 空格翻面 → 数字键评分 → 切换主题 → 检查控制台无报错。

脚本会自动启动预览服务器、跑完关闭，一条命令完成。可通过 `CHROME_PATH` 指定浏览器，`E2E_PORT` 指定端口。

这一层与 jsdom 测试互补：jsdom 验证逻辑与 DOM 结构，真实浏览器验证 IndexedDB 写入、文件下载、CSS 渲染与键盘事件。`readStore()` 会从 IndexedDB 的 KV 表拼回 `{settings, words, daily}` 供断言使用。

### 2.16 `scripts/verify-exe.mjs` — EXE 冒烟（13 项，CI 执行）

以 `WM_HEADLESS=1` + 临时 `WM_DATA_DIR` 启动打包后的 Electron EXE（只起服务、不建窗口），从 `runtime.json` 读取随机端口，校验：启动、引擎与版本、首页注入标记与令牌、8000 词与脚本可访问、无令牌 401、快照、KV 写入、数据落盘、读回、非法 Host 403、正常退出。

### 2.17 `scripts/e2e-exe.mjs` — EXE 浏览器端到端（17 项）

真实 Chrome 访问 Electron 内置服务，验证：启动与引擎、挂载、默认账户与内置词库、便携版模式提示、标记重点后写文件、新建账户、导入 CSV 词库、刷新后账户 / 词库 / 绑定关系全部保留、控制台无异常。

「可独立启动」这一项曾捕获过一个真实 bug：构建脚本用 `String.replace` 注入 JS 时，压缩产物里的 `$&` 被当作替换模式，导致单文件版脚本损坏。详见 `docs/技术架构.md` 第 7 节。

## 4. CI 工作流

### 4.1 `.github/workflows/word-memory-ci.yml`

触发：PR 或 push 到 main，且改动涉及 `word-memory/**`、CI 工作流或 Release 工作流。

步骤：

1. `actions/checkout`
2. `actions/setup-node`（Node 22，启用 npm 缓存）
3. `npm ci`（设 `ELECTRON_SKIP_BINARY_DOWNLOAD=1`，Linux 任务不需要 Electron 二进制）
4. 语法检查：`src/**/*.js`、`scripts/*.mjs`、`desktop/*.mjs`、`desktop/electron/*.mjs` 执行 `node --check`
5. `npm test`（141 个用例）
6. `npm run build`
7. `node scripts/verify.mjs`
8. `node scripts/build-exe.mjs --bundle-only` —— 只跑 esbuild，验证 Electron 主进程可打包，不产出 100 MB EXE
9. 上传单文件版为构建产物（保留 7 天）

超时 15 分钟，并发组按分支取消旧任务。

### 4.2 `.github/workflows/word-memory-release.yml`

触发：推送 `word-memory-v*` tag，或手动指定 tag 重新发布。

权限：`contents: write`（创建 Release）、`pages: write` + `id-token: write`（部署 Pages）。

任务：

**build**（ubuntu-latest）

1. 检出代码、安装依赖（`ELECTRON_SKIP_BINARY_DOWNLOAD=1`）
2. `npm test` → `npm run build` → `npm run verify`
3. 把 `dist/word-memory.html` 重命名为 `word-memory-<version>.html`
4. 生成发布说明（`scripts/release-notes.mjs` 从 CHANGELOG 提取）
5. 上传两个 artifact：`release-files`、`web-dist`
6. 输出 `version`，供 Release 任务复用

**build-exe**（windows-latest，v2.1 新增）

1. 检出同一 ref、配置 Node 22
2. `actions/cache` 缓存 `%LOCALAPPDATA%\electron\Cache` 与 `electron-builder\Cache`（key 绑定 `package-lock.json`）
3. `npm ci`（下载 Windows 版 Electron 二进制）
4. `npm test`（Windows 平台回归）
5. `npm run build:exe` —— esbuild + electron-builder portable
6. `npm run verify:exe` —— headless 启动打包产物，13 项冒烟
7. 校验 `exe-info.json` 的引擎、体积与 SHA-256
8. 上传 artifact：`word-memory-exe`（`WordMemory.exe` + `exe-info.json`，保留 30 天）

超时 45 分钟；首次构建需下载 Electron 与 NSIS 工具，约 3–6 分钟。

**release**（needs `[build, build-exe]`，`if: always() && needs.build.result == 'success'`）

1. 下载 `release-files`；若 `build-exe` 成功再下载 `word-memory-exe`
2. `gh release create` 创建 Release，标题 `WordMemory v<version>`，附件包含：
   - `word-memory-<version>.html`
   - `WordMemory.exe`
   - `exe-info.json`
3. EXE 构建失败时只发布 HTML 并输出 warning，不阻塞常规发布

**pages**（needs build）

1. 下载 `web-dist` artifact
2. `actions/configure-pages` → `actions/upload-pages-artifact` → `actions/deploy-pages`
3. 输出部署地址

## 5. 发布流程

```bash
# 1. 确认基线
cd word-memory
npm install
npm run verify          # 必须全部通过

# 2. 更新版本号
npm version 1.0.1 --no-git-tag-version

# 3. 更新 CHANGELOG.md（新增 ## [1.0.1] - YYYY-MM-DD 段落）

# 4. 提交
git add word-memory
git commit -m "chore(word-memory): 发布 1.0.1"

# 5. 打 tag 并推送
git tag word-memory-v1.0.1
git push origin main --tags
```

推送 tag 后，Actions 会自动完成：Linux 任务出 HTML 与 Pages、Windows 任务出 Electron EXE 并跑 13 项冒烟，最后一起附到 Release。

### 发布前本地自检（建议）

```bash
npm run verify          # 141 单测 + 构建 + 7 项产物校验
npm run build:exe       # 产出 dist/WordMemory.exe 与 dist/exe-info.json
npm run verify:exe      # 13 项 EXE 冒烟
npm run test:e2e:exe    # 17 项 EXE 浏览器端到端（需 Chrome / Edge）
```

CI 会在 `windows-latest` 自动执行 `build:exe` 与 `verify:exe`；浏览器端到端因依赖额外浏览器，仅本地发布前跑。
`dist/exe-info.json` 里的 SHA-256 可用于校验 Release 上的下载文件。

> 版本号请与 tag 保持一致；`build-exe.mjs` 直接读取 `package.json` 的 `version`。
> 也可以在 Actions 页面用 `workflow_dispatch` 指定已有 tag 重新发布（会重新构建 HTML 与 EXE）。

### 版本号约定

| 变更类型 | 版本位 | 例子 |
| --- | --- | --- |
| 破坏性改动（数据结构不兼容） | major | 2.0.0 |
| 新功能（如新增题型） | minor | 1.1.0 |
| 修复与优化（不影响数据） | patch | 1.0.1 |

### 词库更新

如果重新生成了 `data/words.json`（换了词表或改了清洗规则）但没有改动顺序，属于 patch；如果顺序发生变化（用户记录会错位），属于 major，且必须在发布说明中显著提示用户先导出备份。

## 6. 本地排查

**测试失败但看不出原因**

```bash
node --test tests/srs.test.js           # 单文件跑
node --test --test-reporter=spec tests/ # 详细输出
```

**产物校验失败**

```bash
npm run build && node scripts/verify.mjs
```

若「可独立启动」失败，先在浏览器打开 `dist/word-memory.html` 看控制台报错，通常是构建时字符串注入或数据格式问题。

**jsdom 相关报错**

- `Cannot set property navigator of #<Object>` → 不要注入 `global.navigator`
- `localStorage is not available` → JSDOM 需要设置 `url` 选项（非 `about:blank`）

**CI 上 npm ci 失败**

确认 `package-lock.json` 已提交，且与 `package.json` 同步（本地执行一次 `npm install` 后提交 lock 文件）。

**Electron EXE 构建失败**

| 现象 | 原因与处理 |
| --- | --- |
| `只支持在 Windows 上构建` | portable target 产出 PE 文件，请在 Windows 上执行；Linux CI 用 `--bundle-only` 只校验打包 |
| `缺少 electron-builder` | 先 `npm install`；CI 用 `npm ci` 保证 lock 一致 |
| electron 二进制下载超时 | 网络问题；本地可用已有的 `%LOCALAPPDATA%\electron\Cache` 缓存，CI 已加 `actions/cache` |
| `no code signing certificate configured` | 正常提示：未签名会跳过签名，不影响产物 |
| `icon.ico` 相关报错 | 图标由 `makeIcon(256)` 在构建时生成到 `dist/electron-app/`，检查该目录是否存在 |
| `safe-delete / bulk delete` 拦截 | `build.mjs` 只精确清理自身产物，不要改回整目录 `rmSync(DIST)` |
| 生成的 EXE 双击无反应 | 看 `WordMemory-data/wordmemory.log`；若目录不存在，多半被安全软件拦截或无写权限 |

**EXE 冒烟 / 端到端失败**

- `WM_HEADLESS=1` 让 Electron 只起服务、不建窗口；GUI 程序 stdout 不可靠，端口从 `数据目录/runtime.json` 读取（轮询最长 120 秒）
- 若从 Electron 宿主派生的终端启动，需清除 `ELECTRON_RUN_AS_NODE`（测试脚本已自动处理）；否则 `require('electron')` 只返回路径字符串
- `/api/shutdown` 会延迟 150 ms 断开连接再退出，测试脚本对 shutdown 请求做了 `.catch(() => null)`
- 端到端需要系统 Chrome / Edge，可用 `CHROME_PATH` 指定
- 临时数据目录在 `os.tmpdir()` 下，脚本结束时会自动清理

**CI 的 Windows 任务失败但本地成功**

- 检查 `actions/cache` 是否命中了损坏的 Electron 缓存（改 `key` 强制失效）
- `npm ci` 是否成功下载 Electron Windows x64 二进制
- Windows runner 上 `verify:exe` 的 headless 模式会自动禁用 GPU 与沙箱；若仍失败，看构建日志中的 EXE 冒烟输出与 `wordmemory.log`
