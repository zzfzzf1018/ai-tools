# Agent Toolkit Orchestrator

Use this workflow for every user coding task.

## Procedure

1. **Initialization preflight:** before ordinary feature work, automatically read `.agent-toolkit/settings.json` and `.agent-toolkit/settings.schema.json` and validate the settings. The user does not need to explicitly invoke Init. If the file is missing or `initialized` is `false`, run initialization through the `agent-toolkit-init` skill (the `Agent Toolkit Init` agent where the host exposes agents) before continuing. If JSON parsing or schema validation fails, report the specific error and stop; do not use defaults or begin feature work.
2. Read relevant existing requirement records and repository guidance. Create a new, sequentially numbered record in `docs/people-requirements-record/` before implementation. Capture the user's request and material interaction outcomes accurately; redact secrets and sensitive personal information, and never record hidden reasoning. If a number collides, choose the next unused number.
3. Derive the task ID from that record's numeric prefix (for example `0004` from `0004-sample-task.md`) and pass this exact ID plus the record path to the Coder. Do not make the Coder infer or allocate an independent number. The Coder creates, in order, `docs/requirements/REQ-NNNN-<slug>.md` after analysis, `docs/execution-plans/PLAN-NNNN-<slug>.md` and `docs/software-design/DESIGN-NNNN-<slug>.md` after the PLAN, and `docs/tasks/TASK-NNNN-<slug>.md` at task end. All four use the shared ID and same slug; do not overwrite existing documents. See the bilingual toolkit guide for required contents and language/privacy rules.
4. Determine the workflow from `.agent-toolkit/settings.json`; do not assume this repository's branch policy. `developmentWorkflow` selects single-branch, Git Flow, or GitHub Flow. GitHub Flow permits direct `main` work or optional short-lived branches from `main` and user-created PRs; do not automatically create a branch or PR. Git Flow fields are inactive in GitHub Flow. For Git Flow, follow `gitFlow.featureBranchFromDevelop` and `gitFlow.createPullRequestAutomatically`; an automatic feature PR is allowed only with `gitAutomation.autoPush: true`. If required configuration is missing or invalid, stop and ask instead of guessing.
5. Apply `reviewerPolicy`: `every-task` invokes the independent Reviewer for every task; `never` does not invoke it; `on-requested-sealing-or-release-tag` invokes it only when the user explicitly requests sealing or a release tag. If the optional field is absent from an existing schema-v1 settings file, use `on-requested-sealing-or-release-tag`. Keep the Reviewer read-only. When invoked, collect the changed-file list, patch, test commands/results, and acceptance criteria; do not substitute the Coder's conclusions for independent inspection.
6. For explicitly requested Git Flow sealing, follow the configured `gitFlow.sealing` source branch, target branch, pull-request choice, merge strategy, and tagging choice. For sealing in other modes, ask for any missing action details rather than applying Git Flow settings. If the optional policy is absent or incomplete, ask for the missing configuration; do not substitute repository-specific values. A sealing PR requires `gitAutomation.autoPush: true`, and `tagAfterMerge: true` requires `autoTag: true`. Create a tag only from `gitAutomation.tagSourceBranch` (restricted to `main`; use `main` as the safe source when this optional field is absent); if tagging follows a merge, verify the merge landed on that branch before tagging. Before creating a tag, verify it does not already exist locally or remotely. For a release-tag-only request, require explicit user intent and `autoTag: true`, use the configured tag source or the safe `main` fallback, and verify the current branch before tagging. A Reviewer gate is required only when `reviewerPolicy` calls for one.
7. Honor `.agent-toolkit/settings.json` for Git side effects, including `gitAutomation.autoCommit`, `autoPush`, and `autoTag`; applicable permissions and explicit user intent are both required. Never infer permissions from the repository, workflow files, or platform preferences. Do not create a release workflow merely because a GitHub Actions or Azure Pipelines preference is enabled; ask for project-specific build/release details first.
8. On `CHANGES_REQUESTED` from a sealing/release-tag review, return findings for focused fixes and rerun relevant tests before requesting a fresh review. On `BLOCKED`, surface the missing evidence or decision. Ordinary development closes on the Coder's completed self-review and test evidence without Reviewer acceptance.
9. Before closing, check that the four expected files exist, their numeric prefixes match the Orchestrator-assigned ID, and the final Task document links the raw requirement record and all three artifacts. Confirm it records implementation, exact tests/results, review status, Git actions, and remaining risks; do not close with missing or fabricated outcomes. Close with the requirement-record number, task-document link, phase seals, whether conditional review was required/performed, tests and results, Git/release actions performed or deferred, and remaining risks.

## Record format

Use a filename such as `0001-short-task-title.md`, selecting the next unused numeric prefix. Include the date, concise title, user request text, and relevant interaction decisions. Preserve the user's language. Redact secrets and sensitive personal information, and omit hidden reasoning and unrelated chat.

## Operating rules

- Settings are constraints, not suggestions. If a setting is ambiguous or two settings conflict, stop and ask instead of choosing a risky interpretation.
- Do not run automatic release publishing as part of ordinary coding work. Release workflow creation and release publication are separate, explicitly authorized actions.
- Do not make up test results, reviewer findings, or user approval.
- Missing optional structured policy fields on an existing schema-v1 settings file must not invalidate it. If `reviewerPolicy` is absent, use conditional review only for explicitly requested sealing or release-tag work. Missing sealing configuration is not permission to invent branches, PRs, merge strategies, or tag actions; tags remain restricted to `main`.
- Keep each task scoped to its numbered requirement record and the four linked shared-ID artifacts.
